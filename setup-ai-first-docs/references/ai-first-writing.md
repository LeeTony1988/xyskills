# AI-first 文档写作规则

同一份内容，给人读和给 agent 读的写法不同。本文件定义本套文档系统的写法：`plan.md` 面向人的决策，`spec.md` 面向项目级事实，feature spec 面向 agent 的执行，tickets 由用户自由规划。

## 1. 读者决定形态

| 文档 | 读者 | 阅读次数 | 成功标准 |
|---|---|---|---|
| `plan.md` | 人（批准者/维护者） | 通常一次，批准前 | 能判断“做不做、怎么做、风险是什么” |
| `.scratch/<feature>-spec.md` | agent | 每次执行前 | 能把每条规格转成测试或验收动作 |
| `.scratch/tickets/` | agent（按用户规划） | 按需 | 工单格式由用户决定；至少三张独立收尾工单 |
| `AGENTS.md` | agent | 每次会话 | 知道项目规则、文件索引与不能做的事 |
| `spec.md` / `HLD.md` | 人 + agent | 按需查阅 | 查到的就是当前事实 |

## 2. 五条硬规则

1. **结论先行**：每节第一句写结论，再写理由和细节。不要用“随着业务发展……”开头。
2. **指针代替复制**：引用 `docs/spec.md > Boundaries` 并说明为什么读；不把章节内容抄一遍。
3. **编号与稳定 ID**：feature spec 的行为规格 `FR-001`、验收标准 `AC-1`；项目 spec 的 `Success Criteria` 用可测 checklist；工单的命名与编号由用户决定。编号只增不改，删除后不复用。
4. **可验收**：每条规格能回答“怎么证明它成立”。用 Given/When/Then、表格或 checklist，不用“体验良好”“性能优秀”。
5. **命令可复制**：命令写全 cwd、前置条件、期望结果；状态写 `Verified: 2026-05-01, Windows, exit 0` 或 `Unverified: 原因`。

### 2.1 项目 spec 怎么写

`docs/spec.md` 是项目级事实，不是 feature 文档，也不是路线图。固定九节：

| 章节 | 必须回答 |
|---|---|
| `Objective` | 项目是什么、为谁解决什么问题、目标/非目标、用户故事与可测验收标准 |
| `Tech Stack` | 语言、框架、存储、包管理器、版本、锁定策略、关键依赖 |
| `Project Structure` | 源代码、测试、文档、脚本目录的布局与职责 |
| `Commands` | 环境准备、目录创建、依赖安装、构建、运行、测试、Lint、类型检查、发布的完整命令 |
| `Code Style` | 格式化、命名、错误处理、日志、注释、依赖方向，并附好坏例 |
| `Testing Strategy` | 框架、测试层级、位置、覆盖率、fixture、不测试的内容 |
| `Boundaries` | `Always / Ask First / Never`，用项目自己的例子 |
| `Success Criteria` | 项目级、可测、可勾选的完成条件 |
| `Open Questions` | 未决问题、影响、负责人、截止 |

`Commands` 的每一行都必须是可直接复制执行的完整命令，包含参数、cwd、前置条件与验证状态；只写 `npm`、`pytest`、`tsc` 这类工具名不合格。

## 3. `plan.md` 怎么写

plan 是给人做决策的，不是任务清单，也不是接口手册。默认表达是**图**，不是大段文字和宽表格：先让人建立心智模型，再给必要细节。

### 3.1 阅读路径

让人按固定顺序读，降低理解负担：

1. **30 秒摘要**：一句话方案 + 3 条关键决策 + 影响模块。
2. **方案总览图**：一张端到端主路径图。
3. **模块依赖图**：核心模块之间谁依赖谁。
4. **核心接口**：最多 6 行，只列影响决策的接口。
5. **关键机制时序图**：每个机制一张，复杂时改顺序分点文字。
6. **数据对象图**：对象关系 + 关键字段，完整 schema 放 `.scratch`。
7. **验收标准**：可勾选清单。

每节先给结论，图后只写 2–4 句解释；不要逐箭头复述图。

### 3.2 图优先

默认使用 Mermaid，放在代码块里，保证本地/仓库渲染：

| 图 | 回答的问题 | 约束 |
|---|---|---|
| 模块依赖图 `flowchart` | 谁依赖谁、改动边界在哪 | 3–7 个核心模块；箭头 = 依赖/调用；外部系统用虚线；不画文件、类、函数 |
| 机制时序图 `sequenceDiagram` | 一次请求如何穿过模块 | 4–6 个参与者；只画成功主路径；失败/补偿写在图下 bullet |
| 关键流程图 `flowchart` | 端到端主路径和关键分支 | 只保留核心步骤；标注新增/修改路径 |
| 数据对象图 `erDiagram` | 对象之间如何关联 | 只画对象和关系；字段只列关键字段 |

图的规则：

- **一张图只回答一个问题**；不要把架构图、时序图、数据流塞进同一张图。
- **只保留核心模块**：读 plan 的人不需要知道所有类/文件；完整模块清单放 `HLD.md`。
- **命名统一**：节点名与 `spec.md`、`HLD.md`、代码模块同名；不要在图里造新缩写。
- **方向统一**：依赖图从上到下或从左到右；时序图从左到右；全篇保持一致。
- **图能脱离代码读懂**：节点写业务/模块名，不写 `FooServiceImpl`、行号、文件路径。
- **超过 7 个节点或 10 条消息**：拆成多张图，或改成顺序分点文字；不要把图缩小成毛线球。
- **颜色不是信息载体**：新增/修改/外部可以用样式区分，但必须同时有文字/图例；黑白打印也能读懂。

### 3.3 文字兜底格式

流程太复杂、画出来反而难懂时，用顺序分点，不用大图：

1. `[模块 A]` → `[接口/符号]`：[动作]。
2. `[模块 B]` → `[接口/符号]`：[动作]。
3. `[模块 B]` → `[存储]`：[写入/读取什么]。
4. 失败时：[行为与兜底]。

最多 7 步；超过就拆成多个机制，每个机制单独一节。步骤里出现“然后……然后……”时，说明该拆图或拆节。

### 3.4 核心接口

只列影响决策的接口，最多 6 行：

| 能力 | 模块/接口 | 调用方 | 关键约束/错误 |
|---|---|---|---|
| 创建支付单 | `paymentintent.client.PaymentIntents.New` | `checkout.Service.PlaceOrder` | 幂等键必填；`ErrCardDeclined` 转为用户可读错误 |
| 读取配置 | `config.Load` | `cmd/server` | 缺字段返回 `ErrInvalidConfig` |

要求：

- 写到“哪个 SDK/依赖的哪个模块、哪个符号”，不要写“调用支付 SDK”。
- 符号必须真实存在；不确定就标 `Unverified` 并列入 Open Questions。
- 完整参数、错误码、接口清单放 `.scratch/<feature>-spec.md`；plan 只保留人做决策需要的那几条。
- 表格超过 6 行或 4 列，说明你在 plan 里放了执行细节，移出去。

### 3.5 数据对象

- 先用 `erDiagram` 画对象关系，只画对象与关系。
- 每个对象只写：关键字段、所有者/读写、生命周期、存储/一致性、迁移。
- 完整字段表、索引、DDL 放 `.scratch`，不要塞进 plan。
- 禁止只写“用 Redis 存 session”：要写 key 结构、TTL、续期、失效后的用户可见行为。

### 3.6 验收标准

- 用 `AC-1` 编号，每条可独立验证。
- 写用户可观察结果，不写“代码已实现”。
- 覆盖正常路径、边界、失败路径各至少一条。
- 与 feature spec 的 `FR-*` 和 tickets 的验收项可互相映射。

### 3.7 反模式

- 10+ 节点的“架构毛线球”：读者抓不住主路径。
- 时序图里画每个函数调用：那是调试日志，不是机制图。
- 宽表塞满字段、参数、错误码：这是 `.scratch` 的职责。
- 图下用大段文字逐箭头复述：读者会跳过图。
- 图里出现文件路径、类名、行号：代码一改图就过期。
- 多层嵌套子图：人脑工作记忆放不下；拆成多张单问题图。

## 4.  feature spec 怎么写（`.scratch/`）

feature spec 是 plan 的执行展开，不是第二份 plan。

结构要求：

- **头部来源**：`plan.md`、`docs/spec.md` 的 `Objective / Tech Stack / Commands / Boundaries`、`docs/HLD.md` 章节，并写明冲突时以谁为准。
- **目标与非目标**：各 1–3 条，不复述背景。
- **约束只放指针**：技术栈、目录、命令、合规分别指向 spec 章节，不复制原文。
- **行为规格**：`FR-001` 起，每条写 Given / When / Then、边界、错误码/用户提示。
- **接口与数据对象**：只写本 feature 新增或变更的部分；引用 plan 的完整设计。
- **验收映射**：`AC-* → 验收工单或验收说明 → 验证方式`，确保没有 AC 没有落点。
- **同步记录**：最后同步日期与来源 commit。

写作要求：

- 句子短，主语明确；一条规格只说一件事。
- 用表格列举接口、错误码、状态迁移；用编号步骤写流程。
- 不写“参考实现”“类似之前那样”；agent 没有之前。
- 发现 plan 与 spec 冲突时停下提问，不自行选一个。

## 5. 工单：只约束拆分，不约束格式

本 skill 不定义工单模板、命名、字段或状态值；工单由用户自由规划创建，统一放在 `.scratch/tickets/`，不入 Git。

每个 feature 至少三张**独立**工单，不得合并：

| 工单 | 只负责 | 不包含 |
|---|---|---|
| 验收工单 | 按 `plan.md` 的 AC 执行验收，记录命令、输出、结论 | 实现代码、提交代码、更新长期文档 |
| 代码提交工单 | 将本 feature 的代码改动提交到代码仓库，记录 commit | 文档更新 |
| 文档更新工单 | 同步 `spec.md` / `HLD.md` / `roadmap.md` / `status.md` / `plan.md`，并提交文档 | 代码改动 |

规则：

- 实现工单的数量、命名、格式、状态字段全部由用户决定；可以按垂直切片、按模块或按用户自己的方式拆分。
- 实现工单只改代码，不做最终提交；最终代码提交由代码提交工单完成，长期文档改动由文档更新工单完成。
- 推荐顺序：实现 → 验收 → 代码提交 → 文档更新；依赖可按项目调整，但三张收尾工单必须独立。
- 多代码仓库时，每个仓库一张代码提交工单。
- feature spec 的验收映射可以引用工单名称、路径或说明，不要求固定编号。
- 工单只约束职责分离，不约束写作格式；不要因为本 skill 新增模板而被迫使用统一格式。

## 6. `AGENTS.md` 怎么写

- 只放：项目一句话、文件索引、硬约束、`Always / Ask First / Never`。
- 文件索引每行只写“路径 | 内容”，不写“何时读”或阅读顺序。
- 硬约束用肯定句写目标行为；必须禁止时，同时给出正确做法。
- 目标 40–80 行；超过 120 行必须拆分。
- 不写会频繁变化的数字、命令、目录树；这些放 spec/HLD。
- 每个指针都要能在仓库里找到；模式路径用反引号，不做 Markdown 链接。

## 7. 语言与格式

- 跟随项目现有语言；没有先例时用用户的工作语言。
- 术语首次出现时在 `docs/spec.md` 的 `Objective` 或 `plan.md` 中定义；后续只用同一词，不造同义词。
- 日期统一 `YYYY-MM-DD`；状态值只用约定枚举，不写“进行中/开发中”混用。
- 可枚举的事实用表格；原因与取舍用短段落。
- 相对链接用仓库内路径；不链接 `.scratch/` 内部文件。
- 删除营销形容词：强大、优雅、无缝、极致。保留可测的形容词：幂等、可重入、最终一致。

## 8. 反模式

- plan 写成任务清单：那是 tickets 的职责。
- feature spec 复制整段 spec：约束会漂移，读的人不知道以哪份为准。
- 工单写“实现登录功能”：范围过大，无法验收。
- 验收标准写“代码符合规范”：不可观察。
- 接口写“调用 SDK”：无法定位，无法验证版本兼容。
- 数据对象只写字段不写生命周期：并发和迁移一定出问题。
- 文档里放 `TODO` 没有负责人：等价于没有记录。
