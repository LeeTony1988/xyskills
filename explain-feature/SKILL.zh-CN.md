# 解释一个功能

向用户解释功能之前，先读文档和代码：文档说明设计意图和术语，但不能当证据；事实以代码为准。

目标不是复述代码，而是让读者带走一个记得住、能复用的心智模型：先读懂主路径，再按需深入，不是写完整参考手册。按三层递进：

> 形状（架构 + 主流程）→ 机制（3–6 个关键步骤 + 代码锚点）→ 应用（示例 + 反例 + 边界与误解）

抽象概念尽量按“图 → 一句话解释 → 例子”出现；易混概念再补一个反例。连续两个抽象概念没有图或例子，就停下来补一个。

先保证架构图和主流程图；所有权、状态、时序图按需补，不要为了完整而画。

## 0. 先定交付方式

- **默认写文档**：写到 `docs/<feature>.md`。文件名用 ASCII kebab-case，例如 `docs/task-scheduler.md`，不要用 `docs/新功能说明.md`。
- 用户明确只要口头解释时，可以只在聊天中给压缩版；**用户要文档时，绝不能只在聊天里回答**。
- 如果 `docs/<feature>.md` 已存在：先读旧文档，在原文件上修改；不要新建 `-v2`，也不要把第二份解释追加到末尾。

## 1. frame the question

- 用一句话表述本次要解释的 `feature`：**“`<触发>` 使 `<功能>` 经过 `<关键路径>` 产生 `<可观察结果>`。”**
- 用一行写范围：本文解释哪条路径，故意不展开什么。
- 用表格定义容易混淆的词：本文指哪一层、不指什么。

  | 词 | 本文含义 | 不指什么 |
  | --- | --- | --- |
  | task | ... | ... |

## 2. 画架构图

架构图回答 **功能住在哪里、谁依赖谁**。

- 画一张 Mermaid `flowchart`（用 `subgraph` 分层）或组件图，控制在 6–12 个模块；单模块功能用小型上下文图即可。
- 按真实边界分组：用户/UI、宿主/API、扩展/注册表、运行时/调度器、存储、外部服务；子系统内部不是主题时收成一个盒子。
- 每个模块写一句职责和它暴露/消费的接口。边标签写真实契约（`POST /api/...`、`conversation.submit()`），不要写“调用”。
- 用 `-->` 表示同步调用，`-.->` 表示持久化/异步交接；标出谁拥有 conversation、task、document 或 source of truth。
- 加模块表：

  | 模块 | 职责 | 暴露 / 依赖 | 拥有 |
  | --- | --- | --- | --- |
  | ... | ... | ... | ... |

- 说明每个重要边界为什么存在（可替换 / 持久化 / 所有权 / 隔离），并补一段短文：入口、source of truth、host/runtime 边界、哪些模块可替换。

## 3. 画所有权/持有关系图（按需）

只在所有权/生命周期是理解难点时画；否则在架构图里标出拥有者即可。

- 画 Mermaid `flowchart` 或组件图，控制在 6–12 个核心模块。
- 标出创建 / 持有/引用 / 管理 / 使用（但不持有） / 销毁 / 释放。
- 管理模块注明管理结构（`queue`、`array`、`map`、`hash map` 等）。

## 4. 画状态转移图与状态存放表（有状态时）

只在功能有明显状态机时画；状态简单时用一张状态表即可。

- 画 Mermaid `stateDiagram-v2`；每条边写“事件 / 触发者”。
- 用 note 标出每个状态的允许操作与约束，明确非法迁移（如 `Disposed -> Running` 应报错）。
- 状态图后紧接状态存放表：每个状态/数据放在哪、为什么。

## 5. 画完整流程

流程图回答 **按什么顺序发生**。

- 流程叠在架构上：每个步骤写出它由哪个模块负责。
- 从触发点画到用户可见结果，画一张 Mermaid `flowchart`。
- 包含主路径和 hinge point：入口与校验、决策点/状态变化点、终态。
- 标签具体到文件、函数、记录或文档名，不要写“处理”“服务”“流程”。
- 图放在说明文字之前，用散文走一遍箭头，不要把图改写成项目符号清单。

## 6. 画时序图（跨模块时）

只在跨模块的同步/异步交接是理解难点时画；能用流程图说清就不画。

- 参与者用架构图里的模块名，不用文件名；每条消息标真实接口/函数名。
- 同步用 `->>`，异步/返回用 `-->>`；用 `activate/deactivate` 标出谁在处理。
- 异步交接用 `Note over` 标“此处不等结果，结果从 X 返回”；有超时/重试就在图上标出。
- 只画关键往返（5–10 条消息、2–5 个参与者），一张图一条路径；图下用一段散文写关键约束。

## 7. 拆关键步骤

把主干拆成 **3–6 个步骤**，每一步只回答一个决策点。采用**问答笔记形式**：

```text
**xxx 功能为什么这么设计?**

- 解释1
- 解释2
```

- 只在需要代码佐证的步骤贴片段，每步最多一个：3–15 行，标 **简化**，保持接口完整。
- 解释片段的意图、逻辑和使用场景；复杂步骤补一个具体示例或数据。
- 代码位置写成 `path:line`；写之前打开源码核对，不要猜行号或符号名。
- 读者说“还是不懂”时，不要复述。换更小的例子、加反例或类比，并直接改掉那个小节。

## 8. 写文档

默认写到 `docs/<feature>.md`。用户明确要文档时，必须创建/更新文件，不能只在聊天里给解释。

用这个结构（默认 7 节，能删就删）：

```text
# <功能>：端到端

> 定义：<触发> 使 <功能> 经过 <关键路径> 产生 <可观察结果>
> 范围：...
> 术语：见下方术语表

| 词 | 本文含义 | 不指什么 |
| --- | --- | --- |
| ... | ... | ... |

## 1. 架构与所有权
[架构图 + 模块表；补入口、source of truth、host/runtime 边界、可替换模块和关键边界理由；
 所有权/生命周期是难点时追加所有权图]

## 2. 状态与存放（有状态时）
[stateDiagram-v2 + 状态存放表]

## 3. 完整流程
[主流程图；跨模块时序是难点时追加 sequence diagram]

## 4. 关键步骤与代码（3–6 个）
[问答笔记；只给需要代码的步骤贴 3–15 行片段，每步最多一个；标“简化”、带 path:line]

## 5. 具体示例与反例
[一个具体示例/数据走正常路径；给一个易混概念的反例]

## 6. 边界情况与常见误解
[只写相关边界；常见误解短而具体]

## 7. 代码索引
[path:line → 用途]
```

文档规则：

- 用用户的语言写；标识符、路径、协议名保持原样。
- 默认只写一条主路径、1 张架构图、1 张主流程图、3–6 个关键步骤、1 个具体示例；所有权/状态/时序图按需加，分支和边界只在相关时写，不追求覆盖所有情况。
- 每节围绕一个主题；不相关的细节拆出去或删掉。
- 图放在对应说明文字之前；图能说清的，不再用段落复述；代码能说清的，不再逐行解释。
- 关键步骤和对应代码放在一起，按“步骤 → 片段 → 解释”展开；不要把代码集中到单独的“核心代码”章节。
- 状态图与状态存放表放在同一节。
- 深层细节链接已有文档；旧文档在原位置改，不要在末尾追加第二份解释。
- 结束前核对路径、行号和行为结论。

## 9. 收尾

用 3–5 行回顾架构、所有权/状态（如有）和完整流程的形状，点名最容易混淆的部分，并指向能解决它的具体示例。

只给一个下一步深挖建议，不要列一串目录。

## 检查清单

交付前只核对不可妥协项；不适用标 `N/A`。

**范围与结构**

- [ ] 一句话定义 + 一行范围 + 术语表
- [ ] 按 7 节骨架取舍；代码索引齐全；可选图/表不适用就删，不硬凑
- [ ] 用户要文档时已写入 `docs/<feature>.md`；旧文档原地更新

**图与流程**

- [ ] 架构图 6–12 个模块，边是真实契约，标出 source of truth
- [ ] 主流程图从触发点到用户可见结果，每步映射模块
- [ ] 所有权/状态/时序图只在能解释难点时出现；状态图与状态存放表同节
- [ ] 图先于解释，Mermaid 可解析，模块名前后一致

**关键步骤与示例**

- [ ] 3–6 个关键步骤，问答笔记，每步一个问题 + 一个决策点
- [ ] 代码只贴在需要它的步骤旁：每步最多一个片段，3–15 行、标“简化”、带 `path:line`
- [ ] 一个具体示例 + 一个易混概念的反例
- [ ] 边界情况只写相关项

**交付**

- [ ] 结论来自源码，路径/行号已核对
- [ ] 3–5 行收尾：架构/流程形状 + 一个深挖建议

## 反模式

- 从目录树、整个函数或一大段源码开始；先讲细节再给架构。
- 只画流程图，没有架构图：读者看见运动，不知道东西住在哪。
- 每个文件一个盒子，边标签写“调用 / 处理”，没有真实契约。
- 把架构、所有权、状态、流程、时序混成一张图；或每个图都画，不管是否解释得了难点。
- 所有权图只是依赖图重画；状态图没有事件/触发者和非法迁移；时序图按文件拆参与者、同步异步不分。
- 只解释“是什么”，不解释“为什么”。
- 把文档写成代码和图的清单：每个分支、每张图、每段代码都塞进去，读者抓不住主线。
- 关键步骤写成源码逐行导读或四栏字段表，而不是 3–6 个问答笔记。
- 把关键步骤和代码拆成两节，或把整段代码倒进文档；片段不标“简化”、不给 `path:line`。
- 示例只有抽象描述，或只写正常路径，略过相关边界。
- 只给定义、不给反例或常见误解纠正。
- 猜行号，或描述自己没读过的代码。
- 用户要文档，却只给聊天回答；旧文档已存在，却新建 `-v2` 或在末尾追加第二份解释。
- 收尾列一串“下一步可以看……”，而不是一个深挖建议。
